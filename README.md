# doc-qa-rag

Backend-сервис, который принимает PDF-документ, индексирует его в векторное хранилище и отвечает на вопросы **строго по документу**. Каждый ответ содержит ссылки на конкретные места текста: страницу и раздел.

- Поиск гибридный: плотные векторы (смысл) + BM25 (точные слова). Ветви объединяются **внутри Qdrant одним запросом**, после чего кандидатов **обязательно** переупорядочивает реранкер.
- Если в документе нет сведений для ответа, сервис отвечает `found: false` с пустыми цитатами, а не пересказывает общие знания модели.
- Каждый запрос независим: истории диалога нет.

Стек: FastAPI, Celery + Redis, Qdrant, LangChain, Pydantic. Все модели (LLM, эмбеддинги, реранкер) подключаются через [OpenRouter](https://openrouter.ai) одним ключом.

## Быстрый старт

Нужны Docker с Compose и ключ OpenRouter.

```bash
cp .env.example .env              # вписать OPENROUTER_API_KEY=...
docker compose up -d --build      # api, worker, redis, qdrant
curl -s localhost:8000/health     # {"status":"ok","redis":"ok","qdrant":"ok"}
```

Swagger UI открывается по адресу http://localhost:8000/docs.

Минимальный сценарий:

```bash
# 1. загрузить документ → doc_id и task_id
curl -s -F "file=@samples/contract_supply.pdf" localhost:8000/documents
# 2. дождаться state=SUCCESS
curl -s localhost:8000/tasks/<task_id>
# 3. задать вопрос
curl -s -X POST localhost:8000/documents/<doc_id>/ask \
  -H 'Content-Type: application/json' -d '{"question": "Какой ИНН у Поставщика?"}'
```

В `samples/` лежат сгенерированные тестовые договоры и эталонный набор вопросов (см. [Тестовые данные](#тестовые-данные)).

## Архитектура

```
client ──HTTP──> FastAPI (api) ──enqueue──> Redis (брокер + результаты) ──> Celery worker
                    │  ▲                                                        │
                    │  └── состояние задачи ──── Redis ◄──── прогресс ──────────┤
                    │                                                           │
                    ├── /ask: гибридный запрос ──> Qdrant (1 коллекция) ◄── upsert┘
                    ├── реранк ──> OpenRouter /rerank (Cohere)
                    └── ответ  ──> OpenRouter chat (LLM, structured output)
     общий volume /data/uploads: API сохраняет PDF, worker его читает
```

### Индексация (Celery-задача `index_document`)

1. `POST /documents` проверяет файл (сигнатура `%PDF-`, размер ≤ `MAX_UPLOAD_MB`) и сохраняет его в общий volume. Затем ставит задачу и отвечает `202`. В Redis записывается связь `task_id → doc_id`, чтобы отличать неизвестную задачу от задачи в очереди.
2. Worker читает PDF постранично (`pypdf`): не больше `MAX_PAGES` страниц, текстовый слой обязателен. Страницы склеиваются в один текст, параллельно строится карта «где начинается каждая страница».
3. **Разделы** определяются по нумерованным заголовкам уровня 1 и 2 («4. ОТВЕТСТВЕННОСТЬ СТОРОН», «4.2 Штрафные санкции»). Пункты «4.2.1. …» относятся к тексту раздела.
4. **Разбиение**: сначала по разделам, затем `RecursiveCharacterTextSplitter` (LangChain) внутри раздела. Фрагмент никогда не пересекает границу раздела, поэтому поле `section` однозначно. Границу страницы фрагмент пересекать может: факт на стыке страниц не разрывается, у такого фрагмента `page_from ≠ page_to`.
5. **Эмбеддинги** считаются батчами: dense — `OpenAIEmbeddings` (LangChain), sparse — `FastEmbedSparse` с моделью `Qdrant/bm25` и русским стеммингом.
6. **Запись в Qdrant** идёт батчами с `ready=false`. В самом конце всем точкам документа выставляется `ready=true`, только тогда документ виден поиску и списку. При ошибке записанные точки удаляются. Повторный запуск задачи начинается с очистки, поэтому он идемпотентен.
7. Прогресс передаётся через состояние `PROGRESS`: `parsing → chunking → embedding → upserting → finalizing`.

### Ответ на вопрос

1. Проверяется, что документ существует и `ready`, иначе `404`.
2. **Один** запрос `query_points`: в `prefetch` две ветви (dense `DENSE_LIMIT` и BM25 `SPARSE_LIMIT`), у каждой фильтр `doc_id` + `ready`. Объединение выполняет `FusionQuery` (`FUSION=rrf|dbsf`), на выходе `RERANK_CANDIDATES` кандидатов.
3. **Реранкер** (cross-encoder Cohere через OpenRouter) оценивает каждую пару «вопрос + фрагмент» и оставляет `RERANK_TOP_N` лучших.
4. Если даже лучший фрагмент ниже `RERANK_MIN_SCORE`, сразу возвращается `found=false`, **LLM не вызывается**.
5. LLM получает пронумерованные фрагменты `[1]..[N]` и через structured output возвращает `{found, answer, used_fragments}`.
6. Детерминированная постобработка: номера вне диапазона отбрасываются, `found=true` без валидных ссылок превращается в `found=false`. **Цитаты собираются из payload найденных фрагментов**, а не из текста модели, поэтому выдумать цитату модель не может.

## API

| Метод | Путь | Назначение | Успешный ответ |
|---|---|---|---|
| `POST` | `/documents` | загрузка PDF и запуск индексации | `202` `UploadResponse` |
| `GET` | `/tasks/{task_id}` | состояние фоновой задачи | `200` `TaskStatusResponse` |
| `GET` | `/documents` | список проиндексированных документов | `200` `DocumentInfo[]` |
| `POST` | `/documents/{doc_id}/ask` | ответ на вопрос по документу | `200` `AnswerResponse` |
| `GET` | `/health` | доступность Redis и Qdrant | `200` / `503` |

### `POST /documents`

`multipart/form-data`: `file` — PDF (обязательно), `title` — название (необязательно, по умолчанию имя файла).

```json
{"doc_id": "6f1c…", "task_id": "a2b9…", "status_url": "/tasks/a2b9…"}
```

Ошибки: `400` (пустой файл / не PDF), `413` (больше `MAX_UPLOAD_MB`).

### `GET /tasks/{task_id}`

```json
{
  "task_id": "a2b9…", "doc_id": "6f1c…",
  "state": "PROGRESS",
  "progress": {"stage": "embedding", "current": 3, "total": 5}
}
```

`state`: `PENDING | STARTED | PROGRESS | RETRY | SUCCESS | FAILURE`. При `SUCCESS` в ответе есть `result: {doc_id, pages, chunks}`, при `FAILURE` — `error` с понятным сообщением (например, «В документе нет текстового слоя (возможно, это скан)»). Неизвестный `task_id` → `404`.

### `GET /documents`

```json
[{"doc_id": "6f1c…", "title": "contract_supply", "pages": 73, "chunks": 318,
  "uploaded_at": "2026-10-19T10:00:00Z"}]
```

В списке только полностью проиндексированные документы; состояние индексации смотрится через `/tasks`.

### `POST /documents/{doc_id}/ask`

Запрос:

```json
{"question": "Какой размер неустойки за просрочку поставки?", "debug": false}
```

`question` не может быть пустым и длиннее `MAX_QUESTION_CHARS`. `debug` — необязательный, по умолчанию `false`.

Ответ (формат из ТЗ; в цитате также есть `page_to` и `chunk_index`):

```json
{
  "answer": "Неустойка составляет 0,1% от стоимости не поставленного в срок товара за каждый день просрочки.",
  "found": true,
  "citations": [
    {"text": "4.2.1. За нарушение сроков поставки Поставщик уплачивает…", "page": 22, "page_to": 22,
     "section": "4.2 Штрафные санкции", "chunk_index": 97}
  ]
}
```

Если ответа в документе нет: `{"answer": "В документе нет сведений, необходимых для ответа на этот вопрос.", "found": false, "citations": []}`.

С `debug: true` добавляется блок диагностики:

```json
"debug": {
  "dense_hits": 30,          // сколько фрагментов дала dense-ветвь
  "sparse_hits": 30,         // сколько дала BM25-ветвь
  "fused_candidates": 30,    // кандидатов после объединения в Qdrant (вход реранкера)
  "fusion": "rrf",
  "reranked": [              // top-N после реранкера
    {"chunk_index": 97, "rerank_score": 0.93, "fused_rank": 2,
     "in_dense": true, "in_sparse": true, "page": 22, "section": "4.2 Штрафные санкции"}
  ],
  "after_threshold": 3,      // осталось после RERANK_MIN_SCORE
  "used_in_answer": [97],    // какие фрагменты использованы в ответе
  "timings_ms": {"embed": 210, "search": 12, "rerank": 380, "llm": 1700}
}
```

Ошибки: `404` (документ не найден или ещё индексируется), `422` (пустой или слишком длинный вопрос), `503` (OpenRouter или Qdrant недоступны после ретраев). Внутренние детали ошибок наружу не отдаются, они пишутся в лог.

## Принятые решения

**Qdrant через `qdrant-client` напрямую, а не через `QdrantVectorStore` из LangChain.** ТЗ требует LangChain для разбиения, эмбеддингов и LLM, и это соблюдено. `QdrantVectorStore` кладёт метаданные во вложенный объект `metadata.*`, а ТЗ требует плоский payload (`doc_id`, `page_from`, …). Кроме того, нужен явный контроль над `prefetch`/`FusionQuery` и данные для debug.

**Объединение ветвей внутри Qdrant (`prefetch` + `FusionQuery`).** Обе ветви и их слияние выполняются одним запросом на сервере, Python ничего не склеивает. По умолчанию **RRF** (Reciprocal Rank Fusion): он учитывает только позиции в каждой ветви, поэтому ему не важно, что косинусная близость и BM25-оценка лежат в разных шкалах. **DBSF** нормализует сами оценки (по среднему и разбросу) и включается через `FUSION=dbsf`. Сравнение вариантов — в разделе [Оценка качества](#оценка-качества).

**BM25 в Qdrant: IDF на стороне сервера, русский стемминг.** Разреженный вектор хранит частоты терминов, а IDF считает Qdrant (`modifier=IDF`) по всей коллекции. Поэтому при добавлении документов не нужно пересчитывать веса. `FastEmbedSparse(..., language="russian")` приводит «поставки» и «поставка» к одной основе.

**Зачем реранкер, если поиск уже гибридный.** Гибридный поиск сравнивает заранее посчитанные векторы вопроса и фрагмента по отдельности. Cross-encoder читает пару «вопрос + фрагмент» целиком и точнее отличает «неустойку за просрочку поставки» от «неустойки за просрочку оплаты». Он дорогой, поэтому его вход ограничен (`RERANK_CANDIDATES`), а в LLM уходят только `RERANK_TOP_N` лучших.

**Реранкер через OpenRouter `/rerank`, свой класс `OpenRouterReranker(BaseDocumentCompressor)`.** Готовой LangChain-интеграции для OpenRouter-rerank нет. Класс ~60 строк реализует стандартный интерфейс LangChain-компрессора. Один ключ на все модели, образ без тяжёлой локальной модели.

**Порог реранкера.** Если лучший фрагмент нерелевантен, LLM не вызывается вовсе. Это дешевле и даёт вторую линию защиты от ответов «из головы» (первая — промпт и проверка `used_fragments`).

**Цитаты из payload, а не из ответа модели.** Модель возвращает только номера фрагментов, а текст, страница и раздел берутся из Qdrant. Ссылка на несуществующий фрагмент отбрасывается, ответ без валидных ссылок превращается в `found=false`.

**Флаг `ready`.** Сведения о документе хранятся только в payload (реляционной БД нет), поэтому «документ готов» — это `ready=true` у его точек. Частично записанный документ не виден ни поиску, ни списку, а при сбое его точки удаляются.

**Разделы уровня 1–2.** В примере ТЗ раздел — «4.2 Штрафные санкции». Если считать разделом каждый пункт «4.2.1», фрагменты становятся крошечными, а параметры разбиения теряют смысл.

**Страницы склеиваются через `"\n"`, а не `"\n\n"`.** `RecursiveCharacterTextSplitter` режет прежде всего по `"\n\n"`. С таким разделителем ни один фрагмент не пересёк бы границу страницы, и факт на стыке страниц разорвался бы надвое. Это обнаружилось на сгенерированном договоре и закрыто тестом.

**Debug через `query_batch_points`.** По объединённому результату нельзя узнать, сколько дала каждая ветвь. Поэтому в debug-режиме в одном batch-вызове вместе с основным запросом уходят dense-only и BM25-only запросы, и они используются только для подсчёта. Без `debug` выполняется ровно один `query_points`.

**`check_embedding_ctx_length=False`.** По умолчанию `OpenAIEmbeddings` режет текст токенизатором tiktoken и отправляет номера токенов. OpenAI это понимает, а OpenRouter ожидает строки.

**PDF читается через `pypdf` напрямую.** `PyPDFLoader` живёт в `langchain-community`, который выводится из поддержки (DeprecationWarning). Загрузка PDF не входит в требования «через LangChain».

**Ретраи только для временных ошибок.** Сетевые сбои, таймауты, `429` и `5xx` повторяются с экспоненциальной задержкой и jitter (`tenacity`), `4xx` — нет. Встроенные ретраи клиентов LangChain отключены (`max_retries=0`), чтобы попытки не перемножались. Celery-задача тоже повторяется при временной ошибке и подтверждается только после выполнения (`acks_late`).

## Доработки для production

- **Хранение файлов:** S3/MinIO вместо общего volume; удаление исходников после индексации или по политике хранения.
- **Безопасность:** аутентификация (API-ключи/OAuth), rate limiting, лимиты на тело запроса на уровне reverse proxy, антивирусная проверка загрузок.
- **Форматы:** OCR для сканов (Tesseract / облачный OCR), DOCX/HTML; более надёжное извлечение структуры (layout-aware парсер, таблицы).
- **Жизненный цикл документов:** удаление и переиндексация, идемпотентная загрузка по хешу файла, версионирование коллекции при смене модели эмбеддингов (alias + переиндексация).
- **Масштабирование:** отдельная очередь и автоскейлинг worker'ов под индексацию; кластер Qdrant с репликацией и снапшотами; Redis с персистентностью или отдельный result backend.
- **Наблюдаемость:** метрики (Prometheus: задержки по шагам, доля `found=false`, ошибки внешних API), трассировка (OpenTelemetry), структурированные логи с request id.
- **Качество:** регулярный прогон `scripts/evaluate.py` в CI на расширенном эталонном наборе; кеш эмбеддингов частых вопросов; подбор параметров на реальных документах заказчика.
- **Устойчивость к сбоям внешних API:** circuit breaker, резервная модель/провайдер, бюджет и квоты на OpenRouter.

## Тесты и оценка

```bash
uv sync                                  # зависимости, включая dev
uv run pytest -m "not integration"       # юнит-тесты, без внешних сервисов
docker compose up -d qdrant redis
uv run pytest --cov=app                  # все тесты с покрытием (нужен Qdrant)
```

Интеграционные тесты работают с настоящим Qdrant и настоящим BM25, dense-эмбеддинги в них детерминированно подменены, OpenRouter не вызывается.

Проверка доступа к OpenRouter (эмбеддинги, реранк, chat): `uv run python scripts/smoke_openrouter.py`.

### Тестовые данные

`scripts/generate_samples.py` детерминированно генерирует:

- `samples/contract_supply.pdf` — договор поставки на 73 страницы, 13 разделов и ~50 подразделов. В него подложены факты для проверки: точные обозначения (сумма, ИНН, номер пункта, дата), похожие числа в разных местах (0,1% за просрочку поставки в п. 4.2 и 0,5% за просрочку оплаты в п. 7.3), условие, сформулированное иначе, чем в вопросе, и факт, разорванный границей страниц;
- `samples/contract_short.pdf` — короткий договор с тем же вопросом и другим ответом (0,3%) для проверки изоляции документов;
- `samples/golden.json` — 13 эталонных вопросов. Ожидаемые страницы не прописаны руками, а вычислены поиском текста факта в PDF.

### Оценка качества

```bash
uv run python scripts/evaluate.py --out docs/eval-report.md
```

Скрипт загружает образцы (если их ещё нет), задаёт все вопросы с `debug=true` и считает метрики. Цели: вопросы без ответа → `found=false` в 100% случаев; точные обозначения → правильные страница, раздел и значение в 100%; попадание в нужную страницу ≥ 90%.
